Ray Label Management

Single source of truth: node_label drives both K8s pod placement and Ray actor scheduling. Node selection order: CPU/GPU resources first, then node_label as tiebreaker.

1 · Design Principle — One Field, Two Layers

Why a single node_label field?

K8s node labels are provider-specific — there is no universal GPU label. Hardcoding any of them would break across infra providers.

ProviderTypical GPU node label
Cloudera / Liftieliftie.cloudera.com/instance-group-id
EKS (instance type)node.kubernetes.io/instance-type
NVIDIA GFDnvidia.com/gpu.product
GKEcloud.google.com/gke-accelerator

The user supplies the right label for their cluster. The system auto-derives everything else.

Node selection order

Step 1 — Hard resources (CPU / memory / GPU count)
CML sizes the pod. K8s will only schedule it on nodes that have enough CPU, memory, and GPUs. This filters to the candidate set.
Step 2 — node_label (tiebreaker / pinning)
NODE_SELECTOR_KEY/VALUE env vars steer the pod to the exact K8s node within the candidate set. Without this, any node with enough resources is eligible.
Step 3 — Ray actor scheduling
Auto-derived Ray labels (from node_label) pin actors to the same node the pod landed on. Ensures actors don't drift to a different Ray worker.

2 · Automatic Derivation — One Input, Three Outputs

Providing node_label once (in YAML or at request time) produces all three targeting artifacts automatically.

node_label:
"liftie.cloudera.com/instance-group-id": "ig-n4bsnv8r"
→
K8s NODE_SELECTOR_KEY = liftie.cloudera.com/instance-group-id
NODE_SELECTOR_VALUE = ig-n4bsnv8r
Ray node_type:l40-gpu-worker = 1   built-in
accelerator_type:L40S = 1   built-in
instance-group-id:ig-n4bsnv8r = 1   derived

auto = system derives it  |  user = user supplies it  |  Derivation: strip domain prefix from the label key → instance-group-id:<value>

cai_service.py — derivation code

# 1. built-in Ray labels (always)
_ray = {f"node_type:{group.node_type}": 1}
if group.accelerator_type:
    _ray[f"accelerator_type:{group.accelerator_type}"] = 1

# 2. derived from node_label (auto)
_nl = node_label or group.node_label
if _nl:
    for _k, _v in _nl.items():
        _short = _k.split("/")[-1]
        _ray[f"{_short}:{_v}"] = 1

# 3. explicit overrides (optional)
if ray_labels:
    _ray.update(ray_labels)

env["RAY_EXTRA_RESOURCES"] = json.dumps(_ray)

cai_cluster.py — K8s selector output

# launch_worker() — node_label → K8s pod placement
if group.node_label:
    _nl_key, _nl_val = next(
        iter(group.node_label.items())
    )
    env["NODE_SELECTOR_KEY"]   = _nl_key
    env["NODE_SELECTOR_VALUE"] = _nl_val

CML reads NODE_SELECTOR_KEY/VALUE to apply a Kubernetes node-selector to the pod before it starts. This happens at the K8s scheduler level — before Ray even runs.

4 · Application Side — Actor Pinning

Deployment factories inject node_type:<type> = 0.001 into ray_actor_options["resources"]. Actors can also target derived labels for finer-grained pinning.

Factory code (vllm_engine.py)

# node_type from DeployModelRequest
if node_type:
    ray_actor_options.setdefault("resources", {})
    ray_actor_options["resources"][
        f"node_type:{node_type}"
    ] = 0.001

# Result for L40S vLLM deployment:
{
  "num_cpus": 2,
  "num_gpus": 1,
  "resources": {
    "node_type:l40-gpu-worker": 0.001
  },
  "runtime_env": {
    "py_executable":
      "/home/cdsw/.venv-vllm/bin/python"
  }
}

Why 0.001 for custom labels?

ValueMax concurrent actors
1.01 (blocks all others)
0.110
0.001 ✓1000

0.001 = affinity without capacity consumption. Ray's minimum precision is 0.0001.

GPU is a real resource

num_gpus=1 reserves an actual GPU tracked by Ray. Cannot exceed the node's physical GPU count. Custom labels (node_type, derived) are logical only.

5 · AddNodeRequest — Simplified Schema

environment_vars has been removed. node_label is the single field that drives both K8s pod placement and Ray label derivation.

FieldTypeDefaultDescription
node_type str "worker" Logical group name; must match a group in ray_cluster_info.json
cpu int group default CPU cores override. K8s will refuse to schedule if no node has enough CPU.
memory int group default Memory in GB. Same hard constraint as CPU.
gpus int group default GPU count. Real resource — K8s only schedules on nodes with this many GPUs available.
runtime_identifier str group default Docker runtime override.
node_label Dict[str, str] null (uses YAML) K8s node-selector label(s). First entry → NODE_SELECTOR_KEY/VALUE for pod placement. Each entry also auto-derives a short-key Ray resource label (e.g. "liftie.cloudera.com/instance-group-id": "ig-n4bsnv8r" → Ray instance-group-id:ig-n4bsnv8r=1). Overrides YAML node_label when provided.
ray_labels Dict[str, float] null Additional Ray resource labels merged on top of auto-derived ones. Use for ad-hoc affinity not covered by node_label (e.g. {"zone:us-east-1d": 1}).

8 · Key Rules

node_label is the single source of truth. Set it in the YAML once per worker group. It drives both K8s pod placement and the derived Ray labels — no separate fields to keep in sync.
No node_label = any node with enough resources. CPU/GPU count is still a hard K8s constraint. The pod simply isn't pinned to a specific node type.
Label key format is provider-specific — there is no standard GPU label. Use the label your infra provider assigns: liftie.cloudera.com/instance-group-id for Cloudera, node.kubernetes.io/instance-type for instance-type-based targeting on EKS.
Derived Ray label = short suffix:value. Domain prefix is stripped: liftie.cloudera.com/instance-group-id → instance-group-id:<val>. This is what actors target when they need finer-grained pinning beyond node_type.
GPU is a real resource; node_type is logical. Requesting more num_gpus than a node has leaves the actor unschedulable. Custom labels cannot cause this — Ray ignores them if the value is small enough.
Precision floor is 0.0001. Use 0.001 as the standard affinity value for custom labels. 1.0 would limit the node to a single actor of that type.
Labels are immutable at runtime. Once a node joins, its resource set cannot change without restarting the ray node process.
ray_labels is an escape hatch. Use it for ad-hoc labels not derivable from node_label (e.g. zone:us-east-1d if the zone label isn't in node_label). Merged on top of auto-derived labels.
