# Bug Fixes — 2026-03-29

Debugging session covering issues found when running the Ray cluster launch job on CML/CAI.

---

## 1. `start_cluster()` called when head node is already running

**Symptom**
```
❌ Configuration Error: Head node failed to start
Timeout waiting for application <app-id>
```

**Root cause**
`launch_ray_cluster.py` called `manager.start_cluster()` unconditionally. `start_cluster()` always creates a new `"ray-cluster-head"` CML application. When one already existed, CML either rejected the duplicate or the new app conflicted with the running one and timed out after 600 s.

**Fix — three-level guard in `launch_ray_cluster.py`**

```
1. ray_cluster_info.json has head_app_id  →  use it, skip all CML calls
2. JSON missing, but "ray-cluster-head" exists in CML  →  wait for it to become running
3. JSON missing and no CML app found  →  call start_cluster() to create a fresh head
```

Key detail: the check in case 2 must be `if existing_head:` (app exists at all), not
`if existing_head["status"] == "running"`. An app in `"starting"` state would otherwise
fall through to case 3 and create a duplicate, then time out.

**Files changed**
- `cai_integration/launch_ray_cluster.py` — replaced unconditional `start_cluster()` with the three-level guard.

## 2. `CoordinatorService not initialized` on every API request

**Symptom** (management app log)
```
RuntimeError: Coordinator service not initialized
GET /api/v1/resources/nodes  500
```

**Root cause**
In `app.py` `lifespan()`, `CAIService.__init__` raised `ValueError` because `CML_HOST`
was not set. Inside a CML pod the host is provided as `CDSW_DOMAIN` (without the
`https://` prefix), not as `CML_HOST`. The exception was silently caught, `cai_service`
was set to `None`, and `coordinator_service` was never initialised.

Same issue for `project_id`: the code only checked `CML_PROJECT_ID` but the pod env var
is `CDSW_PROJECT_ID`.

**Fix — `ray_serve_cai/management/app.py`**

```python
# CDSW_DOMAIN is the standard CML pod env var; CML_HOST overrides it when set.
_domain = os.environ.get("CDSW_DOMAIN", "").strip()
cml_host = os.environ.get("CML_HOST") or (f"https://{_domain}" if _domain else None)

project_id = os.environ.get("CML_PROJECT_ID") or os.environ.get("CDSW_PROJECT_ID")
```

`CAIService` is now constructed with explicit `cml_host=cml_host` so the derivation
from `CDSW_DOMAIN` is used automatically inside every CML pod.

## 3. `while True: time.sleep(60)` keep-alive loop in head launcher

**Symptom**
The head node launcher script ended with a busy-wait loop to prevent the CML application from exiting:
```python
while True:
    time.sleep(60)
```
This is fragile — if nginx crashes silently, the app keeps "running" but serves nothing.

**Fix — run nginx in the foreground**

Added `--foreground` flag to `start_nginx.py`. When set, after all template rendering
and config setup, the Python process is **replaced** by nginx via `os.execv()`:

```python
os.execv(nginx_bin, [nginx_bin, "-c", str(conf_path), "-g", "daemon off;"])
```

The head launcher template (`ray_head_launcher.py.j2`) now calls
`start_nginx.py --foreground` as the last step. `subprocess.run()` blocks until nginx
exits. If nginx crashes, the subprocess returns and the launcher exits with nginx's exit
code — CML marks the application as failed, giving a clear signal.

**Files changed**
- `ray_serve_cai/scripts/start_nginx.py` — added `--foreground` / `os.execv()` path.
- `cai_integration/templates/ray_head_launcher.py.j2` — removed `while True` loop,
  added `--foreground` to nginx call.

## 4. Job log shows no output — stdout buffering in subprocess

**Symptom**
The CAI job log showed only the Triton/Ray import warnings and then appeared stuck:
```
INFO ... Triton is installed but 0 active driver(s) found ...
INFO ... Triton not installed or not compatible ...
[no further output for minutes]
```

**Root cause**
`launch_ray_cluster_job.py` runs `launch_ray_cluster.py` as a child process via
`subprocess.run()`. Because the child's stdout is a pipe (not a TTY), Python switches to
**block-buffered** mode. All `print()` calls accumulate in an 8 KB buffer and are only
flushed when the process exits or the buffer fills.

The Triton warnings were visible immediately because `logging` writes to `stderr`, which
is line-buffered even in pipes.

**Fix — add `-u` flag**

```python
result = subprocess.run(
    [str(venv_python), "-u",
     str(project_root / "cai_integration" / "launch_ray_cluster.py")]
    + sys.argv[1:],
    cwd=str(project_root),
)
```

`-u` forces Python to run with unbuffered stdout/stderr so every `print()` write appears
in the job log immediately.

**Files changed**
- `cai_integration/launch_ray_cluster_job.py` — added `-u` to subprocess call, fixed
  stale print message (`"bash launch_ray_cluster.sh"` → `"launch_ray_cluster.py"`).
